# 1. Login / Portals

There are two sides/portals:

* Admin
* Shop / Employee

Authentication should remain role-based using JWT.

Do not change authentication unnecessarily if the current implementation already works.

---

# 2. Employee functionality

An employee should be able to:

* View leave balance
* View leave history
* Apply for leave
* View the common company calendar
* View/edit their profile information
* Add/change/remove/delete profile image
* Profile image must have the required format and dimension validation
* Change their own password
* Reset/change password functionality should remain separate from profile information

---

# 3. Admin functionality

Admin should be able to:

* View employee information
* Approve employee leave requests
* Reject employee leave requests
* Cancel approved employee leaves
* Add Management Leave
* Add National Holidays
* Manage employee password for a particular employee

Do not add unnecessary admin functionality beyond what is already present and required.

---

# 4. Leave types and quotas

The employee leave types must be **exactly**:

| Leave Type           | Total Quota |
| -------------------- | ----------: |
| Earned Leave (EL)    |          15 |
| Sick Leave (SL)      |           6 |
| Casual Leave (CL)    |           6 |
| Floater Leave (FL)   |           3 |
| Work From Home (WFH) |          40 |

These values must be treated as the required leave entitlements.

Do not use the old README values.

Do not introduce additional employee leave types.

### Management Leave and National Holiday

Management Leave and National Holiday are **NOT employee leave types**.

They are company-wide calendar events.

Employees cannot apply for them.

They should not appear in the employee leave balance.

They should only appear on the common calendar.

---

# 5. Optional Holiday

The existing project has an Optional Holiday feature.

This is **not required**.

Remove/restructure the Optional Holiday functionality wherever it exists:

* frontend pages/components
* API endpoints
* backend models/services
* database tables/SPs if they are used only for Optional Holiday
* navigation/menu items
* approval functionality

Floater Leave (FL) should be used for the applicable floater/optional-holiday concept instead.

Do not maintain a separate Optional Holiday module.

Before deleting database objects, verify whether they are used anywhere else.

---

# 6. Leave application

Employees can apply for employee leave.

Required leave types are:

* EL
* SL
* CL
* FL
* WFH

Management Leave and National Holiday must NOT be selectable when applying leave.

Leave application must contain:

* Leave type
* Start date
* End date
* Reason
* Half-day option

Reason is mandatory.

Half-day leave must be supported according to the existing implementation/business rules.

---

# 7. Leave approval workflow

Employee applies for leave.

The request goes to Admin.

Admin can:

* Approve
* Reject
* Cancel an approved leave

When a leave is approved:

* The approved leave days must be deducted from the corresponding leave type.
* An email must be sent to all users.

When an approved leave is cancelled:

* The deducted leave balance must be returned.

When a leave is rejected:

* It must not deduct leave balance.

For pending leave:

* Employee can withdraw/remove their own pending leave request.

For approved, rejected, or cancelled leave:

* Employee should only be able to view the record.
* They should not be able to remove it themselves.

---

# 8. Leave balance

Employee dashboard should show a grid containing:

* EL
* CL
* SL
* FL
* WFH

For each leave type show:

* Total
* Taken
* Remaining

Do NOT show:

* Management Leave
* National Holiday

in the employee leave balance.

For display:

Remaining = Total - Approved/Taken

However, when validating a new leave application, make sure pending requests are also considered so that employees cannot create multiple pending requests that exceed their available balance.

---

# 9. Common Calendar

The current project has two calendars:

* My Calendar
* Company Calendar

This is not required.

There should be **ONE common calendar** used by both Admin and Employee.

Remove the unnecessary separation between My Calendar and Company Calendar.

The calendar should initially show the current month.

Users should be able to:

* Navigate to previous month
* Navigate to next month

The calendar should support the following events:

### Employee information

* Employee birthday
* Work anniversary
* Resignation / notice period information

### Leave information

* Sick Leave taken by employees

If applicable according to the existing business rules, show relevant employee leave information on the calendar.

### Company holidays

* Management Leave
* National Holiday

Management Leave and National Holiday should be visually identifiable/faded and should display the reason/details.

The calendar should be common to Admin and Employee, while respecting any necessary visibility/security rules.

---

# 10. Birthday email

When it is an employee's birthday:

* Send a birthday email to all users.
* The birthday employee should also be included.

This notification is separate from the leave approval email.

Do not send unnecessary additional notification emails unless already required by the existing business requirement.

# 11. Leave approval email

Email should be sent **only when a leave is approved**.

When Admin approves an employee leave:

* Send the email to all users.

Do not assume that emails are required for:

* leave application
* leave rejection
* leave cancellation

unless the existing implementation has a technical dependency that must be preserved.

The required business notification is the approval notification.

* Change profile image

Profile image upload must validate:

* Allowed file format
* Required image dimensions

Username and password should remain separate from normal profile information.

Do not unnecessarily mix authentication credentials with profile details.
